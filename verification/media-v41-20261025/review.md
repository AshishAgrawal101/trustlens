# Transparent QR valid-input failure

Confirmed ordinary valid-input failure in native local QR intake. Frozen contract/probe used installed OpenCV encoder with fixed harmless text,264x264 PNGs and existing15-second isolated workers. Transparent source has opaque black QR modules and fully transparent black background; the white reference is its exact alpha composite on white. No downloads, models, destinations or browser uploads.

Actual results:972-byte transparent PNG passed format/size validation but shared decode_image returned solid-black RGB extrema0..0, and production extract_qr returned fixed InvalidImage 'No readable QR code was found.' The1073-byte white reference decoded the exact expected text. Both were generated before scoring; no tuning occurred. results.json preserves actual outputs. Total local probe completed about1.3sec including two ordinary workers, not a model attempt or robustness benchmark.

Root cause: shared ImageOps.exif_transpose(image).convert('RGB') discards alpha instead of compositing. Fully transparent black pixels retain black color channels, so dark modules and transparent background become identical. The same intake issue can affect transparent screenshot text before Windows OCR, but OCR failure was not executed or claimed. Media metadata dimensions remain correct; this is extraction normalization, not readiness falsely claiming native success. Capability copy accurately labels configuration rather than readiness.

Recommended scope for root review: define an explicit background policy for text/QR intake only (e.g. white), preserve alpha until compositing under existing single-flight/pixel caps, and keep image-origin preprocessing/decoder default bit-identical. A generic change to protected shared decoder would silently affect model inputs and must not be made under this fix. Preserve optional alpha/palette-transparency/EXIF orientation behavior and close temporary masks/composites. Paired regression should prove transparent-black/background and ordinary opaque QR both decode identically, while model/default decode remains unchanged. UI can state the chosen extraction background without claiming that all transparent artwork will become readable.

No app edits. This is a concrete supported-PNG extraction gap, not a new detector policy or image-origin accuracy claim. No broader unhandled dependency/readiness defect established in this bounded pass.
