# OCR line-break editing aid proposal (read-only)

Ordinary workflow gap is confirmed. Windows OCR emits each recognized visual line joined with LF; the text rules deliberately treat hard line breaks as clause boundaries. Constructed current-helper probes: 'Please send me your verification code.' → request:code, but 'Please send me your\nverification code.' → no positive evidence; 'Please install TeamViewer.' → request:remote, wrapped 'Please install\nTeamViewer.' → no positive evidence. Existing 'Do not send me your verification code.' remains no positive evidence. These demonstrate presentation-boundary sensitivity, not measured native OCR accuracy. No screenshot or native worker ran.

Current notice says review/correct text and may miss words/punctuation/links. It does not tell a user that OCR preserves visual line boundaries or where to inspect them. Since the original screenshot preview and editable textarea already coexist, a small explicit editing aid can address the workflow without changing detector or automatically joining sentences.

Recommended thin slice: after screenshot extraction, show fixed instruction adjacent to the editor: 'Compare this text with the screenshot. OCR keeps separate lines. If one sentence was only wrapped across the screen, you can replace that line break with a space yourself. Keep real sentence boundaries, punctuation and words such as “not”. Nothing is joined automatically.' Keep the existing mandatory review checkbox and edit→uncheck behavior. Do not tell users to edit until warnings appear; fidelity to the screenshot is the objective.

Optional useful action if a control is warranted: 'Review next line break' (type=button), available only for screenshot OCR review when a hard break exists. On explicit click, focus the existing editor and select the next existing hard break using textarea selectionStart/selectionEnd; wrap search once, give fixed live status 'Line break selected. Compare it with the screenshot before editing.' It must never modify or submit text, check review, infer whether lines belong together, remove negation, or visit links. Support CRLF as one break and existing Unicode hard separators; cap existing text at30000, no stored extra text, reset cursor/status on extraction/edit/file/mode/Clear/exit. This offers an observable way to locate wraps in a long OCR transcript using the existing editor rather than a new reconstruction algorithm.

Minimal acceptance before implementation: (1) split request remains byte-identical after extraction and aid navigation, no automatic detector call; (2) user manually replaces one verified visual wrap, review resets and requires separate confirm/check; (3) actual sentence break and 'not' remain untouched; (4) no-break text gives no misleading action, last-break wraps safely; (5) replacement/mode/Clear/exit removes selection aid state, no private status/export/network. The focused constructed detector probes above should remain unchanged, documenting the unresolved detector boundary rather than tuning it away.

Instruction-only is the smallest fully useful option; navigation is a separate usability enhancement if root chooses it. No app edits, regex exceptions, autojoining, native OCR/model actions, private images or browser uploads performed.
