# Media concurrent decode resource audit

Actionable resource admission gap: /api/inspect/media sends every request to the shared thread pool, and inspect_media invokes full shared image decoding before any admission lock. QR and screenshot extraction already acquire nonblocking single-flight locks before decoding. Per-file64MiB/20MP limits are preserved, but Media has no equivalent concurrent decode bound. Current AnyIO default thread limiter is40 tokens; this is pool capacity, not a guarantee40 images run simultaneously.

Frozen bounded selfcheck (contract.json/probe.py) used only two1x1 constructed PNGs (69bytes each), actual shared decode_image wrapped at the returned RGB ownership boundary with a2-party barrier. Both workers concurrently owned a decoded RGB: peak2, two valid metadata reports, zero remaining owned images. No large allocation, model/native worker, remote request or browser upload ran. This demonstrates missing admission, not an observed OOM.

Why useful: multiple tabs or API requests can overlap independently of each page's disabled Submit. A20MP RGB payload alone represents at least60MB of color samples, excluding Pillow's internal storage, source decode/transposition buffers, input bytes and metadata parsing. With no per-component concurrency admission, ordinary locally parallel files can multiply that footprint; request-body and per-image pixel limits cannot enforce aggregate process memory. Cancellation only stops the client wait; threadpool work may continue, increasing overlap on retry. The UI truthfully warns this, but Media backend remains unbounded relative to QR/OCR.

Smallest proposed closure: nonblocking single-flight Media lock acquired before decode_image, held through metadata extraction/cleanup, released in finally. Fixed dedicated MediaUnavailable busy error mapped to503 in existing intake endpoint. Avoid queueing decoded pixels or changing shared decoder/model limits. Add one coordinated fake-decoder concurrency test proving busy fails before decode and lock releases on success, InvalidImage and optional-metadata failures. Existing serial schema and valid metadata outputs must remain exact. Root may instead choose a small explicit semaphore, but one permit matches existing local QR/OCR policy and requires least new design.

No malformed-image500 or cleanup leak reproduced in this bounded pass. Optional EXIF failures remain null/partial allowlisted results; file/pixel/format validation and owned RGB/header closing are in place. No source changes; original frozen/protected files untouched. This recommendation is a local reliability improvement, not a security claim about a compromised server or an actual measured exhaustion event.

## Authorized Media-only admission closure

Implemented nonblocking Media single-flight admission before shared decode_image and held through the entire unchanged metadata implementation, released in finally. Busy requests receive fixed MediaUnavailable mapped to503 by only the Media intake endpoint. Existing upload read/close finally runs before analysis, including busy errors. Browser controller maps503 to fixed 'Another media inspection is running. Wait a moment, then retry; your selection and caption were kept.' It never echoes backend detail or discards draft/preview.

New tests/test_media_admission.py first run: two expected missing-admission/API failures, two existing failure/retry controls passed. tests/media_admission.test.cjs first failed generic launcher wording. Final61 focused Python admission/context/upload tests and17 focused Media controller/lifecycle/error tests pass, zero skips. An additional metadata-phase failure/retry regression was added after implementation to exercise wrapper finally independently of decoder failures. No old tests weakened; new feedback retained 'retry' to preserve existing meaningful actionability expectation.

Bounded actual-decode regression uses only1x1 constructed PNG and events with2-second test deadlines: first holds decoded ownership, second fails immediately before a second decode, first report matches serial baseline and next attempt succeeds identically. Decode InvalidImage/OSError and later metadata-phase RuntimeError release admission. Endpoint busy503 is input-free and uploaded file is closed. No actual image upload/browser/native worker/model operation ran.

Scope deliberately limited: single-flight bounds concurrent Media decodes/header inspection within one app process only. Upload bytes may already be buffered before admission; it does not cap aggregate request buffering, other tools, multiple processes, or terminate an in-progress inspection when a client cancels. Existing truthful cancellation guidance remains. Shared decoder, 64MiB/20MP policy, metadata schema/interpretation and all model/runtime files unchanged. Original frozen pre-fix probe/results retain historical overlap evidence and were not rerun/rewritten as post-fix output.
