# Fresh communication correctness and usefulness audit

Read-only audit of current text/email/URL/call entrypoints and fixed action/export generation. No app or test source edits, source fetches, private inputs, models, or training. Twelve constructed cases and authored expectations were frozen in constructed-contract.json before any analyzer execution; SHA256 e76344b4a0bb51b2a849fb0ef62daec1612965ce29fd1ec3a170be47f0710351. before-results.json retains every full report, null risk_index, low confidence, timing and inspected source hashes. All cases completed; no outputs discarded. This is a targeted contract diagnostic, not a performance benchmark or fraud/safety truth dataset.

Prior advice/privacy/refusal, horizontal wording/soft-hyphen, link-count cap, email parsing/subject/MIME and URL boundary reports/tests were inspected to avoid reopening repaired cases. Native OCR line continuation, conditional refusal and contact-bank route grammar remain previously documented limitations and are not proposed here. Call uses analyze_text(transcript, 'call') at app/main.py:95–97, so text coverage findings propagate without a separate call analyzer.

## 1. Detected code/device topics can disappear from next steps

**Priority: high usefulness, bounded fixed-guidance correction.** app/guidance.py:40 builds all matched topic actions in dictionary order, then :49 takes relevant[:2]. Payment and overpayment are both before code/remote. `Send $50. Return the overpayment. Send me your verification code.` correctly yields request:payment, request:overpayment and request:code, all high, but actions contain only Pause the payment / Do not return the difference yet / Verify through a separate route. Code-specific privacy advice is absent from both displayed actions and fixed export. Code alone and payment+code controls retain it. The paired call with Install TeamViewer loses device-access advice while retaining callback and two payment actions. No detection miss or falsely safe headline occurs; the high report and evidence remain correct. The actionable gap is that an additional detected payment topic displaces guidance for a distinct credential/device hazard.

Smallest proposed scope: remove the two-topic truncation for these finitely bounded fixed action templates, or deduplicate the money family before selecting other safety domains. Keeping all unique fixed actions is easier to specify and avoids an arbitrary new priority rule; the finite existing REQUEST_ACTIONS bounds output. Keep generic VERIFY/call-back and input-free exports. Do not change scores/rules or invent newly detected topics. Any incomplete-email/manual-review action must not be displaced either.

Acceptance: code alone/payment+code unchanged; payment+overpayment+code contains credential advice; analogous remote/personal/secrecy combinations retain each distinct matched domain; fixed text ordering/deduplication stable; call-back remains first; no private input in share_summary. Existing tests/test_guidance_context.py only checks a two-topic payment+remote combination and therefore does not exercise the cap.

## 2. HTML protocol-relative destinations are silently omitted

**Priority: medium-high coverage.** app/analyzers/email.py:30–33 accepts anchors only if href starts http://, https:// or mailto:. `<a href="//other.example/pay">https://bank.example</a>` returns only url:host:0 for the displayed bank.example label, low/no matched warning, no link mismatch or incomplete notice. The absolute HTTPS control produces both parsed hosts and email:link_mismatch:0 guarded. The destination host is literally present in the supplied protocol-relative href; no remote resolution or base page is needed to observe it. A relative-path /pay control and javascript:void(0) control are also omitted, with no specific unchecked-destination disclosure. These controls do not justify treating relative paths/unsupported protocols as fraud.

Smallest proposed scope: recognize protocol-relative href authority for literal host comparison, using a synthetic HTTPS scheme only internally and explicitly not asserting the original scheme. Validate it through existing strict parser; preserve userinfo/formatting errors. For missing-base relative paths and other unsupported nonempty hrefs, emit a bounded unknown coverage notice/count rather than silently claim inspection or fabricate a host. Do not execute scripts, resolve bases/redirects, expand mailto queries, or inspect page styles. At minimum report unsupported destinations as unchecked even if protocol-relative comparison is deferred. Update email's present statement that message links are inspected as text to state the precise supported subset.

Acceptance: absolute mismatch remains unchanged; protocol-relative same/different literal host controls; missing authority, credentials, hidden characters and malformed brackets never become trusted hosts; relative-path/no-base and unsupported scheme produce unknown partial coverage without a fraud score; empty href/fragment-only normal navigation need an explicit documented policy, not automatic fraud flags; hidden script/style anchors stay excluded; no URL/contact/input text in exports.

## 3. A URL parse failure is evidence, but not a report-level incomplete check

**Priority: medium coverage consistency.** app/analyzers/text.py:194–196 correctly emits url:malformed:N unknown/medium/zero weight when a literal HTTP(S) link cannot be parsed. For `Review https://example.org:bad/notes`, the report remains low with “No strong warning signs matched. That does not verify who sent this or make it safe.” Guidance and export contain generic verify/take-time text; export reports zero warning signs without indicating that a destination could not be checked. Call propagation behaves the same. A malformed bracket plus live code request correctly retains the high code concern but still lacks incomplete-link coverage in summary/export. The evidence detail does say independently check the address; this is therefore incomplete propagation, not total silence or a false proof of safety. The main UI (static/app.js:86–106) only promotes email:incomplete or analysis:links_incomplete to CHECK INCOMPLETE; url:malformed is not included.

Smallest proposed scope: distinguish parse-failed links from over-eight uninspected links, but propagate both as incomplete link review. Retain zero weight/unknown and preserve live concerns. Use a separate count-only coverage reason/evidence or generalize the coverage helper with explicit reasons; do not reuse the current exact “only first 8” copy for a single malformed link. Add fixed manual-address-review guidance/export text without echoing the URL; do not fetch it or normalize it into acceptance. Direct URL mode already rejects invalid addresses, so its validation behavior should stay unchanged.

Acceptance: one malformed link shows incomplete summary/UI/export even with zero positive evidence; valid one/eight links retain existing summaries; malformed+code retains code guidance/high level; text/email/call propagation; combined malformed+over-eight explains both bounded reasons accurately; counts omit private URLs; direct URL strict errors unchanged. Existing tests/test_link_coverage.py covers the first-eight count boundary but not this parse-failure route.
