# Independent backend review

One scope-wording issue reproduced on the full native shared decode path. A constructed9x5JPEG with orientation6 and GPS IFD returns only gps_present=true (no coordinates), but Pillow's ImageOps.exif_transpose internally reserializes EXIF when removing orientation. Its Exif.tobytes calls get_ifd(34853). Instrumentation observed IFD accesses `[34853,34665]` during inspect_media. Thus “no GPS IFD access” is true only for the explicit allowlist helper, not the complete decode pipeline; “coordinates were not inspected” is too broad. This does not expose coordinates, perform a lookup or establish scene location. Recommended minimal correction: state coordinates are not displayed/returned and no location lookup/verification occurs. Root was notified before any app edits; no app source was edited in this review.

The initial isolated GPS unit test deliberately stubbed shared decode to prohibit helper GPS access; it did not establish a full-pipeline claim. Added a full native rotated-GPS fixture test verifying presence-only output and exact allowlist. Added a decoded-image lifetime test verifying close occurs before header reopening. These do not force Pillow's incidental implementation behavior as a permanent contract.

Optional EXIF partial failures cannot leak exceptions/metadata: allowed fields already parsed may remain, subsequent unavailable fields retain null defaults. GPS false means no usable tag observed, including optional parse failure; it must not mean coordinates absent or privacy guaranteed. The current client explicitly says a missing tag does not establish location privacy. It would require a schema change to distinguish absent versus unreadable, and no such stronger backend status is claimed here.

Shared decode validates the complete image before reporting dimensions, using the unchanged64MiB/20MP/Pillow policies. It closes the RGB output before reopening the same immutable bytes for header access. Image.open's context closes the header image. Root added total-body middleware mapping, preventing oversized multipart parsing before route readcap; route closes UploadFile in finally. No model/credentials/network access. The backend parses only DateTimeOriginal, never generic modification DateTime. It reports an unverified clock without timezone; client future-date question is qualified by camera-clock/timezone/editing context, not proof a caption is false. Software/camera strings are editable labels, not trusted authorship or tool execution evidence.

Remaining limits: this is bounded synchronous Pillow parsing in the existing threadpool, not a hard process memory/time sandbox. Requests can still perform the existing maximum-pixel decode; new metadata work is not an inference resource admission. Optional malformed metadata may be rejected earlier by shared image validation. No actual-browser upload, model-origin, human/privacy-history or factual-verification claim follows.
